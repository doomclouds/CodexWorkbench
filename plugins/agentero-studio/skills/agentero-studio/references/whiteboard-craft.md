# 白板表达与布局

用于创建、解释、扩展和整理白板。以下是表达与编辑原则，不是额外的固定审批流程；用户已经明确指定的形式和范围优先。

## 先决定内容以什么形式存在

读者先看整体形状，再逐个阅读标签。画面的组织应帮助他们理解关系：过程按方向展开，循环形成闭环，组成关系按层级或包含表达，几种方案按共同维度比较。不要把所有内容都塞成同样的卡片网格。

一种内容可以由不同对象承担：

| 内容 | 合适的表达 |
| --- | --- |
| 独立概念、任务、事实、风险、说明 | 原生文字、便签或形状 |
| 对象间的因果、传递、依赖和顺序 | 原生箭头及必要标签 |
| 一组内容的边界、阶段或归属 | 分区，或有明确层级的容器 |
| 按相同项目逐项比较 | 表格，不用多组矩形模拟每个单元格 |
| 机器、器件、场所、自然过程中的实物 | 单独可移动的图片；按 [图片与素描](pictures.md) 处理 |
| 示意界面或线框 | 文字与形状；用户要求实际交互时使用 HTML Region |
| 图解、信息密集的架构或数据可视化 | HTML Region，Diagram Design 可用时组合使用 |
| 投票、计算器、可操作原型等 | HTML Region，并明确其交互状态是否需要持久化和共享 |

抽象概念、软件关系、组织关系、时间安排和普通列表不必硬加实物插图。反过来，用户要求看机器如何工作时，几只标签框也不能代替关键实物和部件。用户要作品本身，就做对应的图、草图、场景或可操作内容，不只写几张介绍该作品的卡片。

## 层次与文字

新主题用标题和一句清楚的主旨建立阅读入口。标题是主题，主旨是读者应该带走的意思；不要反复写同一段话。中文以自然、简练、完整的表达为准，不机械套用英文十词等字符预算。

每个对象只承载它需要说明的内容。节点名称、补充解释、数值、协议与技术标签有不同层级；技术值可以用等宽字体，普通中文名称不必等宽。详细背景可以放在相关对象旁、批注或 HTML 区域中，不全部堆在形状中心。

长于标签的文字需要有可读宽度和自然换行。300～400 个画布单位可以作为说明文字的起点，但应按实际字号、中文字符宽度和内容调整；不能依赖单行自动延伸。菱形、圆形等形状的有效文字空间比矩形小，尺寸也需要更宽裕。

名称应在对象上或紧邻对象，而不是远处另设一个需要来回查找的图例。箭头标签用于说明不明显的关系；方向和布局已经足够清楚时，不必给每条箭头再写同义词。

## 颜色与形状要有含义

同一类对象尽量共享尺寸、形状和颜色；差异应指向类别、重点或状态，而非装饰。一个分区用少量有解释的颜色即可，重点应能被识别。原参考中“最多四种标记”可作为克制的提示，不能成为删掉用户所需分类或重写品牌的硬限制。

颜色、边框和线型的含义可通过分区标题、简短说明或图例交代。仅靠颜色表达关键状态会使暗色、色觉差异或黑白导出中的信息丢失。配色细则见 [配色与可读性](appearance.md)。

## 阅读方向、间距与分区

常见中文技术白板从左到右、从上到下阅读。节点对齐、间距一致，并为连线与标签留出专用空间。用户指定时间轴、回路、地图或别的结构时，沿用该结构，不把它强行拉成线性流程。

可以从以下间距起步，再按真实文字和缩放效果调整：邻接内容间约 24，穿过连线的空隙约 64，带说明标签的关系约 144 个画布单位。将相连对象的中心或明确连接点对齐，比事后增加折线更容易读。

分区标题、边框和内部内容需要不同层次。标题放在边界上方或清晰的标题带，内部留白足以容纳文字和连线；别让节点、图片和标签贴着边线。源参考的 24 单位内边距、标题上方约 28 的位置是起点，不是当前渲染器的固定 API。

较长过程不要挤成小字长条。可以继续同一方向展开、分成命名阶段，或换到第二行并清楚标出续接；不要让读者因换行误读顺序。原参考“超过六步换行”是可读性建议，不能截断真实流程。

新白板先让主内容能在一个常见视口内被理解，约 1500×750 可以作为初始构图参考；画布可以继续扩展，不把这个尺寸当作存储或编辑上限。必要时以概览加细节分区代替一屏塞满。

## 新增、扩展与关联内容

先查白板上是否已经有当前主题。补全、延伸或改变其形式，应在原有内容处进行，而不是在旁边再生成一份相同主题。只有新主题，或用户明确指定的位置，才开辟新区域。

新对象放在它们所属内容附近的空白处，可能时兼顾用户当前视口。分区内部新增应落在该分区里；没有空间时可扩充分区或向画布右方、下方展开，不直接覆盖其他对象。

添加图片、表格、链接或 HTML Region 时，把整体尺寸、标题和相关说明一起纳入构图。链接卡片通常比小节点宽，不应为了硬塞进去而缩到不可读。已有相同引用时不重复添加。

作品引用应使用 Studio 实际返回的稳定资源或可用链接。不要虚构旧宿主的 artifact URL，也不因为无法打开某个来源对话就另外复制作品。用户需要本地文件时，交付实际导出资源。

## 修改与清理

人的布局常常承载尚未写出的思路。修改前读取当前内容与目标版本；保留对象身份、手工分组、用户文字、颜色与未涉及的区域。不是只保留“看起来相同”的内容，而是保留可继续引用的原对象。

一次改动可能直接影响别处：同一名称的重复标签、由数值算出的结果、依赖前一步的说明、连接该对象的关系。按用户任务核对这些直接后果，不能任意扩展为全板重做；没有证据时也不编造新的数值。

“清理一下”应优先解决实际遮挡、溢出、拥挤、混乱的连接和不一致，而不是只回复建议。按范围批量调整位置和尺寸，只写本次改变的字段。整体移一组内容时，把所属对象、覆盖其上的注释或贴纸、相关连接一起考虑，不擅自解组。

图形或图片中的内部部件不能通过移动整张图片单独调整；此时需要重绘图片，或在 HTML Region 源码中改动。不要为了方便把已有图片悄悄转换成多块不同内容。

写前检查锁定和正在编辑的状态：`locked: true` 的对象不能移动或删除，不能先改成未锁定来规避；用户已明确解锁时再按任务处理。对象正被输入时，结合发起人和明确任务来源判断，避免覆盖另一成员尚未提交的内容。对象版本仍然匹配不等于获得了移动、删除或覆盖输入的授权。

程序也应以锁定、编辑状态和版本检查保护这些行为，但不能在尚未确认实现时假定工具一定会拒绝。不能通过重建整板、删后重加或改写存储文件绕过锁定与冲突。工具拒绝时说明具体对象和原因。

## 讨论、建议与实施

用户要解释、比较或梳理，且已明确要求更新白板时，应把答案落实到板上，再简短说明做了什么。用户只是问事实、讨论可行性或询问“你会怎么做”，不自动产生白板修改授权。

用户要求选项时，读取 [建议方案与预览](ideas.md)。先提供有差异的方案和可判断的取舍，不先把其中一个永久应用。直接命令“把这几个风险分组”则属于实施，不必转成方案选择。

创建已获授权的新白板时及时落盘并打开；完整覆盖必要步骤、标签和关系，不为缩短等待而漏掉组成部分。仅在业务含义、操作范围或最终产物会实质变化时澄清，已有上下文能确定的细节自主处理。

## 完成与验证

根据改动验证实际结果。字段校验与写入确认说明数据被接受，视觉检查说明当前画面可读，交互测试说明功能可用，它们不能互相代替。普通小改无需重跑整套检查，新增图解、嵌入脚本、暗色显示或复杂重排应检查对应行为。

回复让用户知道改动位置、关键假设、是否保存以及仍缺什么；不要用命令或 JSON 代替完成说明。不要严格限制回复必须两句，也不把“图能显示”说成所有共享、导出和平台都已验证。
