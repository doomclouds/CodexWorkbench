# 建议方案与预览

在用户询问“你会怎么改”“接下来做什么”“给几个方案”时读取。直接要求“整理这些便签”“补三项风险”“采用第二种”属于已授权实施，不应无故改成一次方案访谈。

Studio 已通过 `artifact_feedback` 提供建议方案，入口在房主的批注面板，未应用的提案对局域网访客隐藏。使用下列公开操作，不写入旧 `data/users/me/idea`，不复制旧 CLI 流程。若连接到旧版工具且 schema 尚无这些操作，退回聊天建议并说明；不能声称界面已经出现并不存在的预览。

## 公开操作

- `suggest`：提供作品 ID、观察 `text`、2～4 个 `options`；每项包括 `label`、可选 `description` 和产品操作 `operations`。为新增对象提供稳定 ID；修改已有对象必须携带实际读取的 `expectedVersions`，整作品操作携带 `expectedRevision`。提案会保存生成时的基线。
- `preview`：提供反馈 ID 和选项 ID，返回只读的 `document` 投影。不写入作品、不生成修改历史或内容广播。界面悬停和键盘聚焦使用它。
- `choose`：提供反馈 ID 和选项 ID，应用该项；已经选中的项目再次选择时安全撤回。相交选项在一次事务中切换，不相交选项可同时应用。
- `withdraw`：只给反馈 ID 时清除整个建议，保留已应用内容；带选项 ID 时撤回该项的修改。
- `list`：房主可取得自己的提案。其他分享角色不会取得提案、源码快照或通过事件间接看到提案内容。

重复写入使用同一 `operationId`。出现冲突时读取最新内容、重新形成方案，不拿新版本号为旧提案强行背书。建议有约 30 分钟的可见生命周期；用户正在聚焦选项时界面延后自动清除。

## 建议从当前白板出发

先读当前作品和相关对象；刚刚已经读到同一版本时无需机械重复。成员可能在等待期间新增或改变内容，不能只凭上一次印象判断这块白板仍然空着。

空白板没有现成内容可供修改，应简要说明，并根据标题和对话提出适合开始的内容；确实不知道用途时再澄清。不要拿默认模板当作用户已经选择的方案写进去。

非空白板的建议应立足一个具体观察，例如缺少负责人、流程缺少回路、两组内容难以比较，而不是泛泛地说“可以美化”。先区分读者要补事实、改善组织还是换表达方式，避免只有几套不同配色。

## 两到四个有差异的选项

通常提供 2～4 个完整、可判断且互有区别的选项，最可能适合的放在前面。这是给选择留出空间的实用范围，不要求在只有两种合理做法时硬凑四种。

每个选项应有：

- 一句基于现有内容的观察，说明它针对什么问题。
- 明确的目标对象或区域，避免含糊的“优化一下”。
- 简短且彼此不同的行动名称，让用户只读名称也知道会改变什么。
- 简要收益与代价，包括哪些信息是假设、哪些事实还需确认，不能编造负责人、数值或承诺。
- 一组明确的变化，覆盖必要的新增、更新、删除及相应关系，使方案本身完整。

选项之间可以在形式上真正不同：把零散便签组织为流程、按风险类别分区、转成比较表、用插图解释实物、或把当前关系放入 HTML 图解。不要把文字相同、只改颜色的三个版本当成三种思路。

## 正式的建议预览应如何工作

建议是房主可见的临时提案，和所有成员共享的正式内容分开：

1. **私人入口。** 在批注面板显示带锚点的建议卡片，其他成员不会看到尚未选择的草稿。保存权限不足时，不转写到共享评论或其他人的空间。
2. **预览。** 指向或选择一个选项时显示它会改变的内容，离开或取消后恢复正式白板；单纯预览不生成正式内容修改、历史记录或共享广播。
3. **应用。** 用户明确选中后，检查该方案依据的对象版本，再一次提交对应变化。其他成员看到的是已应用结果。
4. **撤回选择。** 已选选项可以撤回，但撤回只影响它自己的实际修改；后续有人改过的对象不能用旧快照覆盖。
5. **多个选项。** 不相交的选项可以并用；触及同一对象的方案需要互斥或明确合并，不能简单叠加造成内容冲突。

公开工具没有这套能力时，聊天中提出的方案仍然有效，但必须称作聊天建议；用户在对话选择后，再按普通编辑工作流读取当前内容并执行。

## 快照与修改边界

提案需要保存它所依据的对象身份和读到的内容／版本，而不只是一个模糊的整板时间戳。用户可能隔一段时间才应用；当前对象有变化时，程序必须指出冲突，不能静默把后来的改动覆盖掉。

新增元素使用新的稳定身份，组内连线同时映射到新身份；不同选项的新对象不能共用会碰撞的 ID。删除需考虑连接和附属内容。提案中同一对象不能被重复指定为相互矛盾的操作。

原提案只允许有限的字段更新、少量嵌入和有界负载，以避免建议成为任意代码或存储写入入口。Studio 的提案能力也应有明确的允许操作和体积校验；不能因为普通 `artifact_apply` 能更新 HTML 或图片源，就假定任何内容替换都能安全用于临时预览。

如果提案没有声明支持表格内容、HTML 源或媒体替换，不偷偷用其他字段绕过；可以改为说明方案，等用户选择后通过正常内容编辑操作执行。一个无效变化不应让界面半应用同一方案的其他部分，实际提交应遵守程序的原子性约束。

## 生命周期和会话选择

同一位置只保留清楚可辨的当前建议，避免多批过时入口堆在画布。更新建议应基于它自己的版本；撤回或过期只清理建议，不删除用户已经应用的内容。

原实现包含用户清除、不能解析和约 30 分钟可见后的自动清理，并在菜单展开时延后。迁移时保留“有明确期限且不干扰正在选择”的语义；实际期限和接入以 Studio 程序为准，不能在 Skill 里凭空宣布某个计时器已经运行。

用户在对话说“就用第一种”时，核对指的是哪批建议、是否已在界面应用，以及相关对象是否仍是方案所依据的状态。不要重复执行已经点击过的方案；也不把另一人私人的第一选项当成当前用户的选择。

成功创建了可见建议时，简短说明建议所在位置即可，不必在聊天重复整套选项。只有聊天建议可用时，在聊天完整给出选项和取舍，不让用户寻找不存在的标记。缺少权限或方案无法保存时说明失败，不悄悄改写其他位置来绕过权限。
