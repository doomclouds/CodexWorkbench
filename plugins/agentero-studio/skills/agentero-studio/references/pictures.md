# 图片与素描

在白板上绘制或重绘实物、场景、示意插图、图标、平面图和分镜时读取。本文件迁移原白板的实物表达方法；专业图解可继续组合使用可选的 Diagram Design，不要求安装它才能画普通插图。

## 一张图应当包含什么

先区分“独立对象”和“完整场景”。用户可能单独拿起、移动、缩放或删除的实物，适合成为一个单独的图片或 HTML 区域；地面、底图与放在上面的东西也可以分开。彼此遮挡、光照和空间关系构成一个整体的场景，适合保持为一张图，不能拆开后留下空洞。

图片表示事物的外观，关系仍由白板承担：实物之间的传递、流程或循环用箭头连接；事实、步骤、数值和不能靠外观解释的部件放在相关文字或框中。风、声、热、光等输入输出可以用少量有方向的波形或笔迹提示，并说明它代表什么。

不要把一整块教学白板压成一个无法分清对象和关系的大插图，也不要在需要看实物的任务里只画几只文字框。用户明确只要一幅插画、一个图标或一个完整场景时，按该产物自身组织，不额外包进一圈解释卡片。

主体应明显大于辅助对象。原参考的主体宽约 320～480、辅助对象约 160～260、独立展示的大图约 800 个画布单位，可以作为构图起点。最终尺寸依内容、文字和当前视口调整，保持图像宽高比，不作为硬上限。

## 选择载体

- 使用 `image` 时，图片整体是白板对象。适合已有图片、独立插画和不需要内部交互的 SVG。旁边的原生标签、箭头和说明可单独编辑。
- 使用 HTML Region 时，SVG 内部可以有文字、分组、语义标识和样式，用户通过标注让 Codex 修改内部部件。完整 HTML 源是事实来源，不另维护一份相同的原生节点模型。
- 用户要可操作原型、投票或计算器时，用 HTML Region；一张静态图片不能冒充可操作产品。是否持久保存输入还要按 [对象与协作操作](operations.md) 的状态协议处理。
- 需要照片、位图或已有素材时，使用实际获得的素材或当前可用的图像生成能力。不要给没有取得的图片编造路径或资源引用。

## 先列清楚看得见的东西

解释实物时，先确定主对象、相关对象、必须显示的关键部件，以及这些部件如何支持用户的问题。对机械结构、器件和自然物体，应体现真实形态与必要环境；需要解释内部原理时可用剖面或局部放大。

一个短计划通常只需四项：实物各自是什么、哪些事实需要框或文字、对象间如何连接、每个实物有哪些能被认出的部件。不要先写长篇绘画宣言，但也不能为赶时间忽略使对象可识别的结构。

细节应该解释对象，而不是填空。例如外壳的接缝、按钮、开口、支架、线缆、屏幕内容、容器的口沿、运动方向，能让读者理解尺度、用途和作用。不要把未经核实的内部结构、端口或尺寸画成确定事实；示意应标清示意性质。

## 干净绘图与手绘表达

优先采用用户指定的风格。未指定时，需要精确、可比、按比例理解的几何图、平面图、电路示意、曲线、标志和图标适合干净绘图；用于解释实物外观和场景的插图可以采用设计素描或马克笔风格。

干净绘图侧重正视、清楚轮廓、规整尺寸和稳定的线宽。构造辅助线与实体轮廓有区别，颜色克制；比例和位置有实际含义时，不能为了漂亮随意改动。标志或图标以少量有辨识度的大形状构成，不用密集碎线模拟细节。

手绘表达需要形体、透视和细节，而不只是给所有边线加随机抖动。原项目的自动马克笔渲染属于其编辑器能力；Studio 没有实际支持时，不能仅添加旧 `data-look` 属性就宣称获得了同样笔触。SVG 本身可以表达所需色块、轮廓和细节，或使用实际支持的绘制方式。

## 马克笔／设计素描的构成方法

1. **先定形体。** 用清楚的整体轮廓建立一个焦点，保证比例一致。略高的三分之四视角有助于显示顶面、正面和侧面；近处压住远处，部件的圆口、转轴和弯曲面用方向一致的椭圆表现。
2. **铺主体色块。** 用两三种主要颜色，其他地方可以留白。色块可以略超出暗面轮廓，亮面留出高光，不必逐像素填满。独立插画可以用一个更宽、较低的对比色块托住主体；解释白板上的单个对象通常不需要额外背景装饰。
3. **增加同色深浅。** 受光面、背光面、凹陷与底部形成层次。可用浅色底配中间色的低透明度遮盖，深处再加重；不能把透明阴影直接叠在完全透明背景上，导致暗色模式出现意外颜色。
4. **画主轮廓。** 用比细节稍粗的连续轮廓说明体积、遮挡与主要开口。原参考约 2.5 的轮廓线宽和约 1.2 的细节线宽可作相对比例，不强制等于实际显示像素。
5. **补解释性的细节。** 接缝、螺钉、旋钮、通风口、导线、把手、折痕和屏幕符号要服从同一透视。细节线应足够让主体真实可辨，又不抢过焦点。原参考对主体约 40～60 个形状／笔画、配角约 15～25 个的量级，是避免过度简陋的提醒，不是凑数量的验收标准。
6. **最后检查阅读。** 轮廓、颜色、阴影和说明是否共同解释用户关注的部位；删去只增加噪声的装饰，保留真正帮助识别和理解的细节。

可使用柔和的蓝、橙、黄、绿、紫或中性灰，再从所选主色生成深浅层次。颜色不必固定为旧项目那组六色；使用用户品牌时保持品牌。深色部件和投影不能与当前背景融为一片，浅色部件也需要可见边界。

## 剖面、分镜与场景

剖面应让关键工作部件彼此可辨，适合用有含义的色块和轮廓区分，并在附近标名。不是每一块零件都需要独立颜色；同类部件的处理应一致。

分镜图可以是一幅横向连续画面，每格有边界、相同的角色或物体尺度和清楚的动作变化。空间提示保持简练，让每格里承担叙事的物体足够大。时间顺序与普通对象关系不能混用，必要时加编号或简短字幕。

概念插画可以借真实场景解释抽象意思，例如桌面上的工具、装配中的部件或正被分类的材料。道具应服务概念，不机械要求每张图必须有十五件东西；也不因旧参考偏好而禁止用户明确要画的人物或其他主题。

## 标签、箭头与坐标

图的名称靠近图，重要部件的说明靠近对应部位。原生图片可以在外部放文字，再以短箭头指向部件；HTML Region 内可直接用可标注的文字和稳定目标 ID。不要照搬旧编辑器禁止 `<text>` 的限制。

标签最好与目标大致水平或垂直，站在最近的空白边缘，缩短引线并避免交叉。文字不应盖住要解释的形状；多个标签共同围绕一张图时，先分配左右两侧位置。

新图片的 `viewBox` 建议从 `0 0` 开始，宽高比与显示尺寸一致。已有 SVG 可能从 `(minX,minY)` 开始；若图像原点是白板 `(x,y)`、显示尺寸为 `(w,h)`、内部坐标为 `(u,v)`，在没有额外留白、裁剪或旋转且宽高比一致时，对应白板点为 `(x + (u-minX)*w/viewBoxWidth, y + (v-minY)*h/viewBoxHeight)`。其他情形应按实际渲染变换定位，不能机械套用这个公式。图片移动或缩放后要重新计算纯坐标引线，不把图片内部坐标误当整板坐标。

一个新解释区可把主图放在区域的局部原点附近，标题在上方。周边说明与流程从这里展开；不要把负坐标或固定原点当作所有已有白板必须重排到的位置。

## SVG 与资源的有效性

SVG 应是完整闭合的图形，具有正确命名空间和 `viewBox`。数据 URI 需要正规编码，特别是 `#`、`%`、`&` 等字符；不要复用旧解析器要求的“一行、单引号、最多若干组／透明度”等私有约束。

图片中的 SVG 与 HTML 内联 SVG 的样式能力不同：作为图片加载时，外部脚本不会成为交互，也不能指望它继承白板的 `currentColor`。需要跨主题的线条可使用明确的主题版本，或在 HTML 内联 SVG 里使用区域自己的 CSS 变量。

导入的图片或 SVG 可能引用外部字体、图片和 CSS。按当前沙箱与资源协议处理；不能因为在开发机能看见，就声称 LAN 访客和离线导出也完全一致。所需资源缺失时说明或修复，不悄悄删除关键内容。

## 组合示例：雨水收集装置

用户要解释“雨水怎样流到花盆”时，可以把收集口／储水桶作为主图，把阀门、软管与花盆作为相关对象；标题在上方，一句主旨说明流动路径。箭头说明水流，框或文字说明过滤、储存和浇灌步骤，不把连接线画死在一张不能分别移动的大图片里。

如果用户只要一张完整的装置插画，储水桶、管道和花盆在同一空间内叠放，就用一张场景图；如果需要给桶内液位、阀门或管道逐一备注，可以使用包含稳定标识的 HTML/SVG 区域。示意未给实际尺寸时，不添加虚构的压力、容量或效率数据。

## 修改一张已有图片

移动和缩放只更新相应字段，保留资源、裁剪、链接、视频封面和作者信息。重绘则替换该图片的源，必要时一起调整与 `viewBox` 对应的宽高；不得把重绘当成删除同区域其他对象的理由。

无法可靠修改的位图或已由用户手工重绘的图，应保留原图，按用户要求重绘或请求必要素材。不要通过反复编码／解码、重新截图或低分辨率覆盖，让原有清晰度和可编辑来源丢失。
