# 卡帕西编程准则

这些准则源于 Andrej Karpathy 对大语言模型编程常见失误的观察。需要在谨慎和速度之间取舍时，偏向谨慎。微小任务按实际情况判断。

## 1. 先想清楚，再写代码

明确前提，有疑问就说出来，把影响方案的取舍讲清楚。

- 实施前说明会影响结果的假设。如果有几种合理理解，说明它们会怎样改变做法或结果。
- 如果存在更简单的办法，指出来。有充分理由质疑某个做法时，直接说清问题和理由。
- 有疑点时先核对代码、调用方和已有测试。授权内可逆的实现选择，自行判断并验证。若仍涉及授权边界，或需要用户决定业务行为、公开契约等实质取舍，再就该点澄清。

## 2. 简洁优先

选择能解决当前问题、让维护者容易读懂的实现。

- 只实现任务要求的功能。一次性用到的代码直接写，按实际需求决定是否引入配置或扩展点。
- 错误处理针对实际可能发生的失败。
- 在行为和可读性相同的前提下，选更简单的实现。复查时看哪些分支、状态或转发可以省去，同时让读者仍能顺着代码看懂业务过程。

## 3. 只改必要的地方

编辑已有代码时，沿用现有风格，将改动限于完成任务所需的范围。顺手发现的无关死代码可以指出，保留相邻代码、注释和格式。清理本次改动导致无用的导入、变量或函数。

逐行核对修改，每一处都应能追溯到用户的要求。

## 4. 以可验证的目标推进

把任务改写成能检查的完成标准，根据验证结果继续调整，直到达到目标。根据任务选取验证方式，例如下面三种做法。

- 「添加校验」→ 用测试检查无效输入，再让测试通过。
- 「修复缺陷」→ 用测试复现问题，再让测试通过。
- 「重构某段代码」→ 确认相关测试在重构前后均通过。

多步任务可先给出简短计划，为每个关键步骤配一个检查，例如「实现该步骤 → 核对预期结果」。具体的完成标准能让你自行推进和复查。「让它能用」这样的目标容易在实施中反复需要澄清。
