# 作者与方法来源

本文件用于追溯和继续完善技能。日常写作按主文件及对应方法说明执行，无需每次访问原文。下面记录的是对具体作品的编辑性提炼，不是对作者所有文章的概括，也不新增写作规则。

借鉴可迁移的方法，再用适合当前材料的中文表达。保持统一的作者态度，不拼接作者口头禅，不逐段切换人设，不复制原作的故事、笑话或独特句子。原文的技术判断与示例条件也不会自动成为其他文章的事实。

## 稳定作者态度的主要参考

### 陈皓

参考：[《如何做一个有质量的技术分享》](https://coolshell.cn/articles/21589.html)、[《我做系统架构的一些原则》](https://coolshell.cn/articles/21672.html)。

提炼：围绕读者需要交代问题，对重要取舍明确表态，让判断有条件、有理由、有代价。用于作者的责任感和判断力。保留对读者的平等关系，不迁移论战式措辞或将个人经验当成普遍定律。

### Julia Evans

参考：[Simple explanations without sounding condescending](https://jvns.ca/blog/2020/11/15/simple-explanations-without-sounding-condescending/)、[Making hard things easy](https://jvns.ca/blog/2023/10/06/new-talk--making-hard-things-easy/)。

提炼：把困惑当作值得解释的事，尊重读者的理解能力，允许作者表现出好奇和发现新关系的欣喜。用于平等、亲近和共同观察的感觉，不把解释简单化为居高临下的教学。

## 阅读推进与兴趣的补充参考

### Robert Nystrom

参考：[Garbage Collection](https://craftinginterpreters.com/garbage-collection.html)、[Observer](https://gameprogrammingpatterns.com/observer.html)。

提炼：围绕眼前需要解决的小问题引入概念，让每一步解释带来进展，轻松旁白贴近当前内容。用于复杂内容的推进和解释中的松弛感，避免把每节都写成同一种戏剧结构。

### Joel Spolsky

参考：[Making Wrong Code Look Wrong](https://www.joelonsoftware.com/2005/05/11/making-wrong-code-look-wrong/)、[The Law of Leaky Abstractions](https://www.joelonsoftware.com/2002/11/11/the-law-of-leaky-abstractions/)。

提炼：具体的起点承担解释任务，类比有可辨认的对应关系，后文回访开篇时获得新的含义。用于动机、类比和呼应；引用个人经历需要事实来源，类比不能代替机制。

### Raymond Chen

参考：[The Old New Thing，2020-05-20](https://devblogs.microsoft.com/oldnewthing/20200520-00/?p=103775)、[The Old New Thing，2022-08-16](https://devblogs.microsoft.com/oldnewthing/20220816-00/?p=106994)。

提炼：从一个局部异常进入，用必要线索解释原因，再落回可理解的后果；冷静旁白形成轻微幽默。用于短距离的好奇心和及时揭晓；假设推演必须保留假设身份。

### Josh Comeau

参考：[What The Heck, z-index??](https://www.joshwcomeau.com/css/stacking-contexts/)。

提炼：让读者先形成预期，呈现与预期不同的结果，引入解释后再回到同一问题。用于预测、参与和检验理解。原作交互演示的效果不能全部归于文字，Markdown 只迁移适合自身载体的方法。

### 张鑫旭

参考：[属性选择器相关原文](https://www.zhangxinxu.com/wordpress/2015/06/ie7-attribute-css-selector/)。

提炼：由真实的技术反差带动叙述，使用自然中文旁白，解释之后再回扣起点。用于中文的亲近感和局部反转；不迁移过密的网络用语，也不为轻松而降低精确性。

### Bartosz Ciechanowski

参考：[Mechanical Watch](https://ciechanow.ski/mechanical-watch/)。

提炼：从够用的理解开始，每次补充都回应此前尚未解释的问题，逐渐看到整体及其巧妙。用于进展感和对好设计的欣赏。原作视觉与交互贡献很大，不据此要求每篇文章配图或制作应用。

### 小林 coding

参考：[键入网址到网页显示，期间发生了什么？](https://xiaolincoding.com/network/1_base/what_happen_url.html)。

提炼：让一个连贯过程连接多个概念，持续说明当前获得了什么信息、下一步为何发生。用于减少术语跳转造成的断裂；叙述连贯仍需保持真实对象和职责的区别。

### Randall Munroe

参考：[Relativistic Baseball](https://what-if.xkcd.com/1/)。

提炼：明确假设，沿其后果继续推演，用尺度或预期的反差形成冷幽默，再回到起始问题。用于条件推演和局部幽默。这里只借鉴写法，不将原作推算视作当前材料的事实依据。

### Tim Urban

参考：[Why Procrastinators Procrastinate](https://waitbutwhy.com/2013/10/why-procrastinators-procrastinate.html)。

提炼：从熟悉的困扰建立共鸣，让少量稳定的意象帮助读者追踪冲突与变化。用于亲近感、记忆线索和情绪起伏。解释性角色保持比喻身份，不把虚构角色当作真实机制。

## 交付表达的补充参考

参考 Piebald-AI 仓库整理的 Claude Code 提示片段：[Writing for the user](https://github.com/Piebald-AI/claude-code-system-prompts/blob/main/system-prompts/system-prompt-writing-for-the-user.md)（标注版本 2.1.247）与 [Outcome-first communication style](https://github.com/Piebald-AI/claude-code-system-prompts/blob/main/system-prompts/system-prompt-outcome-first-communication-style.md)（标注版本 2.1.315）。它们是第三方提取记录，不是 Anthropic 官方写作规范。

提炼：最终交付能独立理解，先交代结果与判断，再提供必要依据；通过删去无关细节保持简短，保留完整、自然的句子。对应方法归入理解过程与复查说明。这里不迁移英文句长、词数阈值、禁用标点或固定注释行数等机械限制，也不改变项目已有的中文表达偏好。

## pstack 的技术写作与编辑

pstack 用 Diátaxis 区分学做、办事、查阅和理解四种需求。它从 Google 开发者文风、简化技术英语和 Global English 中选取具体做法，例如用真实名称、将条件放在动作前、让限定词紧靠对象。这里按读者用途检查中文成稿，操作写到读者能判断下一步，参考条目经得起单独查阅。英文词数与语法细则留在原语境。[pstack 技术写作](https://github.com/backnotprop/pstack/blob/427e37b2903f8ab2c8c836b79af7c785c90f70d2/skills/technical-writing/SKILL.md) · [Diátaxis 对四种需求的说明](https://diataxis.fr/start-here/)

pstack 的 unslop 提醒作者检查模糊来源、泛化的效果评价、替同一对象轮换名称，以及没有新内容的总结。这里把这些判断用于复查，回到材料寻找具体行为、观察或数值。材料允许多少确定性，文字就保留多少。中文解释里的节奏、类比和轻松感仍按实际阅读效果处理。[pstack 的编辑规则](https://github.com/backnotprop/pstack/blob/427e37b2903f8ab2c8c836b79af7c785c90f70d2/skills/unslop/SKILL.md)

## 继续补充来源时

先读作者的实际作品，再说明哪一种写法解决了什么阅读问题、有哪些使用条件。将可执行的方法归入对应参考文件，来源记录保留原文链接和必要边界即可。

选择能增加新能力或校正现有方法的来源。作者名单长短不代表技能质量，也无需为了覆盖更多作者而给正文增加手法。
