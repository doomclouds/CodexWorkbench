# 工作台插件开发

为 CodexWorkbench 的插件作出一致、可解释的开发决策。工作台以现有 Codex 桌面端为宿主，由可组合的本地插件逐步构成。

## 理解需求与启动实施

- 结合当前请求、已有决策和仓库实际情况，识别任务阶段、期望结果、范围与完成标准。讨论或评审交付分析与建议；明确的实施任务按授权范围修改。调用本 Skill 本身不代表创建插件、安装或发布的授权。
- 先查看与问题相关的现有实现和记录。用户工作流、数据归属、公开契约、兼容范围或最终产物存在关键歧义时，说明选择及推荐，在依赖它的实现开始前澄清；等待期间继续不依赖答案的调查与准备。不要自行补出业务需求后开工。
- 已有决策和技术基线能确定的细节直接采用，无需重复询问或机械复述。用户提出的方案与目标、宿主能力或维护成本不匹配时，用具体依据说明问题并推荐替代方案；不要悄悄替换明确要求。

## 已确定的约定

- Windows 和 macOS 都是目标平台。普通 TypeScript／JavaScript 使用跨平台的 Node.js 与 Web API，不按操作系统重复实现，也不预先添加无用途的平台分支。
- 前端采用 TypeScript、React、Vite；后端采用 Node.js、TypeScript；仓库采用 pnpm workspace。暂不使用 C#。
- 插件默认通过 Git 仓库的远程 marketplace 安装；提供实际插件目录与可直接启动的运行资源，不默认制作 ZIP 安装包，也不要求最终用户先构建源码。
- 界面支持明亮、暗色两套主题。MCP App 跟随宿主；Web 页面在没有可用宿主主题信号时跟随系统，并提供明亮／暗色／跟随系统选项。
- 支持 MCP App（Widget）和 Web 两种界面形式。MCP App 可按需提供 Global、Thread、File 入口及 inline／fullscreen 呈现；Web 默认在 Codex 内置浏览器打开。
- 每个插件按需求选择形式和扩展点，不要求提供所有入口。多个入口共享业务逻辑、数据契约和适合复用的组件。
- 插件原型以目标平台的真实 Codex 截图为宿主参考，分别校准 Windows 与 macOS 的顶部菜单、标题、标签及窗口控件；不把 DSH 宿主外壳或 macOS 样式直接套到 Windows。插件只设计宿主允许的内容区域。
- 使用官方 MCP、MCP Apps、OpenAI Extensions、WebMCP 和浏览器 Annotation 等公开能力。不要用未公开的 Codex 内部接口作为常规基础。
- 本地优先，插件默认数据根目录为用户主目录下的 `.codexworkbench/<plugin-id>/`，与源码、安装目录分开。具体存储格式随业务决定；插件通过公开接口与稳定资源引用协作。

这些是当前基线，可在后续沟通中修订。不要把新的建议、某个参考项目的做法或单次实现细节直接提升为全仓库要求。

## 作出选型

关键需求足以支持选型后，给出推荐方案及决定它的实际约束。下列维度只讨论本次新增、变化或尚未确定的部分，沿用已有决策的小修改无需重新设计：

1. 用户从哪里进入、如何完成工作；Agent 需要读取什么、执行什么。
2. 使用 MCP 工具／资源、MCP App 或内置浏览器 Web 中的哪些部分，以及选择哪些扩展点。
3. 数据、界面状态与上下文分别属于全局、工作区、资源还是当前对话。
4. 页面关闭、切换对话、Codex 退出后，工具和后台任务如何处理。
5. 主题、宿主能力、平台依赖与数据写入有哪些实现约束。
6. 如何从远程商城安装的插件验证 Windows、macOS 与所声明的入口。

按任务复杂度缩减说明，不把这份清单当作每次必须填写的设计模板。需要用户决定的取舍在相关实现前提出；目标明确后，自主完成常规实现细节。

## artifacts 记录与续接

- 产物按 `artifacts/<plugin-id>/<version>/` 组织，再按用途分目录，具体规则见 [工程与交付约定](references/engineering.md)。目录在实际写文件时递归创建，已有目录复用，不生成空目录或占位文件。
- 每个版本可以有 `DESIGN.md`，也可以没有；按复杂度和后续使用价值决定，不强制为每个版本或小修改写设计文档。
- 将有续接价值的重要决策、影响后续实施的待定事项和关键验证结果及时更新到已有记录；按需附上产物位置、当前状态和下一步。不逐条转录聊天，不为简单答复或小修改新建一套记录。
- 长任务接近上下文压缩或交接前，立即落盘续接信息。可用 `artifacts/<plugin-id>/CURRENT.md` 指向当前版本与设计文档；未写完整设计文档时，也可在这里保留简短状态。
- 恢复任务时先检查该插件的 `CURRENT.md` 和所指记录，再核对 Git 与实际文件，避免重做已完成工作；记录不替代当前实现证据。
- 设计文档与设计产物保留在被 Git 忽略的 `artifacts/`，不加入提交；不自动修改忽略规则或强制加入 Git。正式采用的图标等运行资源在实际实现时再复制到插件资源目录。

## 实现边界

- MCP Server 提供可脱离界面使用的业务工具；WebMCP 提供依赖当前实时页面的操作。需要界面时，两者调用现有业务逻辑。
- Global／Thread／File 是入口；inline／fullscreen 是显示方式；stdio／Streamable HTTP 是 MCP 传输方式。分别设计，不混为插件类型。
- MCP 与 Web 接入层负责各自的宿主交互，不让业务模块直接依赖宿主全局对象。网页在内置浏览器打开不等于自动拥有 MCP App API。
- 对话推理由 Codex 完成。插件若需要后台调用模型，单独定义服务接口与凭据，不假设可复用 Codex 登录态。
- 一个插件拥有自己的数据写入逻辑；其他插件通过公开操作访问，不直接修改其数据库。
- 日常实现保持小而具体；先复用现有代码，出现真实复用需求后再提取共享包。

## 查询与证据

- OpenAI／Codex 接口先使用官方文档工具搜索，再读取原始页面；不可用时使用官方站点。
- 第三方库的用法先用 Context7 解析 Library ID，再查询匹配版本；不足时补充官方文档或官方仓库，说明覆盖缺口。
- 如确需查询 .NET 官方资料，优先使用 Microsoft Docs 工具；这不改变当前不使用 C# 的技术基线。
- 查代码时优先使用项目已有且可用的 CodeGraph 索引；文档、配置或索引未覆盖的内容直接读取。索引缺失不应阻塞普通开发，也不因本 Skill 自动安装工具。
- 把“官方文档支持”“当前宿主实测通过”“实验待验证”分开记录。SDK 示例和截图不能替代实际兼容性验证。
- 现有约定变更时，更新拥有该规则的文件，并检查受影响的引用和 UI 元数据；通用协作偏好留在全局 AGENTS.md，仓库执行规则留在根 AGENTS.md，本 Skill 维护插件决策与实现边界。依赖具体 SDK 版本的参数从当前官方文档核实，不在本 Skill 复制整份接口手册。
