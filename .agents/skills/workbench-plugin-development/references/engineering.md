# 工程与交付约定

## Windows 与 macOS

两端都是正式目标。常规 JS 使用一套实现，不为普通页面、数据处理和 Node API 引入平台判断。

实际涉及操作系统的部分再隔离适配，例如原生模块、系统文件选择器、凭据存储和进程管理。此时检查依赖的 Windows／macOS 支持及需要交付的 CPU 架构，不用未经验证的“JS 项目天然跨平台”代替证据。

- 构建与分发检查脚本优先使用 Node.js；不让开发流程依赖 PowerShell-only、Bash-only 命令或开发机全局工具。
- 用 Node 路径 API 处理本地路径，用 URL API 处理 URL；文件路径不直接拼成 URL。
- 不硬编码盘符、用户名、路径分隔符或源码目录外的参考仓库位置。
- 文件命名与 import 大小写保持一致；用户选定的数据目录允许空格、中文及其他 Unicode 字符。
- 需要启动外部程序时传递参数数组，管理超时、取消与退出；不要把用户输入拼成 shell 命令。
- 在对应系统的用户数据／配置目录保存运行数据，允许用户为内容库选择目录。源码、插件安装目录与可写数据目录分别处理。

这些检查集中于真实边界，避免给纯界面修改增加无关平台工作。

## 工具与数据操作

- MCP 工具声明有意义的参数、输出结构和读写副作用；注解是描述，不代替后端授权和输入校验。
- 列表分页或限制结果大小，长文本和大文件按需读取；不要把整个知识库一次送入模型上下文。
- 结果中使用稳定 ID、来源和定位信息，使 Agent 可以继续读取、验证或引用。
- 对可重试写入考虑幂等，对并发编辑使用合适的版本检查，避免静默覆盖用户修改。
- 原生设置与 Thread 可能使用不同 MCP 进程。共享配置变更必须能被其他实例重新读取；真实宿主验收覆盖跨实例同步，不能只验证单进程模拟桥。
- 耗时操作按需要提供任务 ID、状态、进度和取消；明确关闭页面或退出宿主后是否继续。
- 文件访问约束到用户选择或授权的范围，处理真实路径和符号链接边界；UI 隐藏按钮不代替后端检查。
- 本地 Web 服务默认限制本机访问，明确端口、启动和退出方式；需要对外访问时另行设计连接与认证。
- stdout 留给 stdio 协议，日志使用 stderr 或日志文件。日志不记录密钥和无关的完整用户内容。

## 界面约定

共享语义主题、基础控件和常见交互。新增组件库先检查现有共享组件与宿主样式能力，避免各插件维护一套不同的按钮和表单。

考虑加载、空状态、错误、重试、保存中和保存失败。Thread 面板适应窄宽度，操作支持合理的键盘路径与焦点反馈。不同入口可以调整布局，不必强行复制相同页面结构。

不把后端协议、SDK 参数和构建细节显示在普通业务流程中；用户需要处理连接或故障时再提供可操作的诊断信息。

## 依赖与代码变更

- 遵循仓库已有实现，补齐功能所需的最小修改。发现真实共享需求后再提取公共代码。
- pnpm 管理统一锁文件；可执行项目声明实际依赖，不依赖其他包偶然提升到根目录的依赖。
- 不通过运行 `latest` 的临时安装命令隐含升级整个项目；升级时核对使用中的版本与兼容关系。
- 依赖的许可证、原生模块、Worker／WASM 与最终包加载方式影响交付时，纳入选型说明。
- 重要的新运行时、共享服务、数据格式或公开契约变更记录原因与迁移影响。普通实现细节无需逐一写决策文档。

## artifacts 目录规范与沟通落盘

统一按“插件 → 版本 → 用途”组织产物，不在顶层混放插件名、日期、设计图和验证记录：

```text
artifacts/
└─ <plugin-id>/
   ├─ CURRENT.md                # 可选：当前版本、状态与下一步
   └─ <version>/                # 例如 v0.1.0，设计目标版本不等于已发布
      ├─ DESIGN.md              # 可选版本设计文档
      ├─ manifest.json          # 有多项产物时按需记录索引与来源
      ├─ prototypes/            # 界面原型、流程图
      ├─ assets/                # 候选图标、图片等设计素材
      ├─ prompts/               # 生成提示词及修正记录
      └─ validation/            # 实测记录、检查报告、验收截图
```

目录创建与命名规则：

- 使用与插件一致的稳定 kebab-case ID；版本目录使用目标版本，例如 `v0.1.0`。版本尚未确定时可使用 `draft`，不能因此声称已经发布。
- 只在写入实际文件时递归创建所需父目录。已有目录直接复用，不提前创建整棵空树，不添加 `.gitkeep` 或空设计文档。
- 原型建议使用 `<platform>-<screen>-r<revision>.png`，例如 `windows-reading-r1.png`；图标可用 `icon-r1.png`。文件修订号与插件版本分开。
- 提示词放入 `prompts/`，用同名文本或明确的 JSON 索引关联对应图片。验证记录可在文件名中带日期，不以日期替代插件／版本目录。
- 新版本建立独立目录；同一版本的文档可更新。保留有价值的原始参考和旧修订，不自动清空、批量移动或覆盖历史产物。
- 路径基于仓库根目录和路径 API 计算；插件 ID、版本只作为安全的单个目录名，拒绝路径分隔符和越级路径。真实需要全仓库产物时，可用保留目录 `_workbench/<version>/`，仍按需创建。

设计文档按需存在。建议只记录目标与范围、已确定的决策、方案、验证证据、未解决事项、产物链接和下一步；不要复制整段聊天或堆积工具输出。用户改变重要决策、发现关键依赖或阶段完成时，及时更新现有记录。上下文接近压缩或任务交接前，保存能让后续 Agent 直接继续的状态。

`CURRENT.md` 是可选的轻量续接入口，说明当前版本、阶段、重要文件、最近验证和下一步。记录“建议方案”和“已确定事项”的区别，明确设计图不是运行截图、设计版本不是已发布版本。

`artifacts/` 继续由 `.gitignore` 排除。设计文档不加入提交，落盘也不等于已上传 GitHub；不使用 `git add -f` 或修改忽略规则来绕过这条约定。官方参考原图等长期开发资料按其来源和许可保存在 `docs/references/`，与版本设计文档分开维护。

恢复工作时，先读取当前插件的续接入口和相关版本文档，再检查实际文件与 Git 状态。参考记录中的临时目录、进程和外部依赖仍需重新确认，不能把过去的成功当作当前可用状态。

## 检查与测试

实际建立运行代码时，提供清楚区分的格式检查、lint、typecheck、test、build 和包检查入口。命令只有在仓库实现后才能报告为已执行或可用。

测试关注关键行为：数据写入与恢复、迁移、并发、工具契约、路径边界、入口生命周期，以及用户与 Agent 共用的主要工作流。文案、轻量样式或纯规范修改不为凑覆盖率增加测试。

按插件声明的能力验收：

- Global：打开、再次打开、资源定位与应恢复的状态。
- Thread：切换对话、多实例、上下文与草稿的归属。
- File：打开、读取，声明可编辑时验证保存和冲突处理。
- Web：直接打开 URL、刷新与深链接、服务断开，以及使用中的 WebMCP／Annotation 能力。
- 主题：明暗切换及使用中的组件和嵌入内容。
- 平台：Windows 与 macOS 从商城安装后的启动和主要工作流。

可以用 CI 或对应平台实机完成适当检查；只在 Windows 运行通过时，不宣称 macOS 已验证。报告已执行的检查与仍未验证的范围，不重复运行无新增价值的检查。

GitHub 自动工作流仅在推送 Git 标签（tag）时触发，不监听普通分支推送、Pull Request 或手动启动。日常修改在本地检查；后续新增的自动构建和发布流程同样遵循 tag 触发规则。

## 插件商城分发与版本

每个插件独立版本化，默认通过远程 Git marketplace 分发。用户添加远程商城后安装其中的插件，不制作 ZIP 安装包或把“下载、解压 ZIP”作为默认使用流程。只有用户另行明确要求时才增加其他交付渠道。

商城清单引用实际存在的插件源目录，按宿主官方格式维护；插件目录含所声明的清单、入口、Skills、资源及可直接启动的运行文件。需要构建的 TypeScript／前端由开发者预构建，将安装所需运行文件纳入 Git；开发依赖、缓存、用户数据与无关中间产物不进入插件目录。

从临时复制的插件目录或商城安装缓存运行冒烟检查，确认离开源码工作区后不依赖 pnpm install、构建命令、未声明依赖或开发机绝对路径。MCP App 的 HTML、字体、Worker、WASM 等资源按实际 CSP 和宿主加载方式核实。单文件 HTML 是可选构建方案，不强制所有二进制都内嵌。

安装说明声明 Node 等必要外部运行条件；需要外部 CLI 的插件明确由用户安装，插件负责诊断，不隐含自动安装器。MCP 配置使用宿主支持的插件根路径机制。运行资源与源码必须保持一致，变更后重新构建并检查；不要把预构建运行文件笼统当作可忽略缓存。

只在运行资源存在且验证后，才把插件加入可安装商城。修改源目录后通过宿主流程刷新／重装，不直接编辑安装缓存。自动检查与构建仍仅按推送 tag 触发，不因采用商城分发恢复普通 push／PR 流水线。

用户内容、密钥、日志、`node_modules/`、中间构建输出和 `.codegraph/` 不提交。商城安装实际需要的预构建运行文件属于交付源码的一部分。安装或发布按当前任务授权执行，不把创建项目 Skill 当作发布授权。

## Git 与规范维护

新建分支默认使用 `codex/` 前缀。提交使用 Conventional Commits，scope 可用插件 ID；保持修改范围清楚。是否提交或推送按当前任务要求，不继承参考仓库的自动提交指令。

本 Skill 是当前项目开发基线。用户明确改变约定时，更新最接近该规则的文件，并检查其他参考是否冲突。尚未确定的具体插件功能、业务数据格式、精确依赖版本或组件库，在对应任务中讨论，不以占位决策提前锁定。
